# design-kit

A framework-agnostic CSS design system and Open UI component library. Ships pure CSS (no runtime), a curated SVG icon suite, and a Vite-powered visual workshop deployed to GitHub Pages.

## Architecture

Three tiers of design tokens, each layer consuming the one above:

1. **Primitives** (`src/tokens/primitives.css`) — raw scales on `:root`: spacing, type, radii, motion, shadow. No colors.
2. **Semantic contracts** (`src/tokens/semantic.css`) — intent tokens (`--color-primary`, `--color-bg-surface`, …) with a dark baseline on `:root` that acts as the fallback when a theme leaves a token unset.
3. **Theme presets** (`src/themes/*.css`) — concrete palettes scoped to `[data-theme="…"]` (and `:root[data-theme="…"]` for specificity over the baseline). A theme overrides only the tokens it changes; everything else cascades from the semantic baseline.

Components (`src/components/*.css`) style Open UI anatomy classes (`.ui-btn`, `.ui-field`, `.ui-panel`) and native elements (`<dialog>`, `[popover]`, `<details>`, `<progress>`, `<meter>`, `<table>`, `<input type="range">`, `<input type="file">`) and read only Tier 2 tokens — never raw primitives or hex. Variants are driven by `data-*` attributes (`data-variant`, `data-size`, `data-intent`, `data-state`). Native form/status elements are restyled through their vendor pseudo-elements (`::-webkit-progress-value`, `::-moz-meter-bar`, …), so those rules are duplicated per engine. The native switch (`<input type="checkbox" switch>`, `.ui-switch-native`) is restyled through the standard `::track` / `::thumb` parts inside `@supports selector(::thumb)`; outside that query it takes the `.ui-checkbox` look, which is what engines lacking the parts render. Where an engine has no pseudo for a part (WebKit has no `::-moz-range-progress` equivalent for a slider's filled track), the component falls back to a gradient driven by an optional `--ui-*` custom property the app sets, and reads correctly with the property unset. Three components layer a progressive enhancement on top of a working baseline through `@supports`: `select.ui-select` styles the classic control, and an `@supports (appearance: base-select)` block in `form.css` restyles the picker through the `::picker(select)`, `::picker-icon`, `::checkmark`, and `selectedcontent` pseudo-family in engines that ship it (Chromium 135+); `.ui-combobox-listbox` positions itself absolutely inside its root, and an `@supports (anchor-name: --a) and (anchor-scope: --a)` block anchors it to the field where CSS anchor positioning is available. `.ui-carousel` is a working `scroll-snap` strip on its own, and an `@supports selector(::scroll-marker)` block grows its arrows and dots out of the scroller itself — `::scroll-button(inline-start|inline-end)`, one `::scroll-marker` per item with `:target-current` as the current one, gathered into `::scroll-marker-group` (Chromium 135+) — so an app on a supporting engine renders no controls at all, and `data-controls="app"` suppresses the generated pair where it wants to render its own.

`src/index.css` is the entry point: it `@import`s tokens then components, and adds the reset, base `body`, and focus-ring rule.

## Build & run

- `npm run dev` — Vite dev server for the workshop (`workshop/`).
- `npm run typecheck` — `tsc --noEmit` over `workshop/`.
- `npm run check:contrast` — `scripts/check-contrast.mjs` runs the WCAG AA gate over every `src/themes/*.css` and exits 1 on a failure (see WCAG below).
- `npm run build:icons` — `scripts/generate-icons.mjs` regenerates `src/icons/svg/*.svg` and `sprite.svg` from `src/icons/icon-data.js` (see Icons).
- `npm run build:css` — `scripts/build-css.mjs` copies `src/` → `dist/` verbatim (relative `@import`s resolve inside `dist/`). No bundling or minification.
- `npm run build:workshop` — `vite build workshop` → `dist/workshop/`.
- `npm run build` — typecheck, contrast gate, icons, css, workshop, in that order, so a type error or a failing pairing stops the build before anything is emitted. CI (`.github/workflows/deploy-workshop.yml`) runs this on push to `main` and publishes `dist/workshop/` to Pages.

`dist/` and `workshop/dist/` are gitignored; the workshop dev/build reads `src/` directly, not `dist/`.

## Icons

`src/icons/icon-data.js` is the single source of icon path data (`name → SVG inner markup`). Both consumers read it directly, so the copies can't drift:

- `scripts/generate-icons.mjs` (the `build:icons` script) imports it and writes `src/icons/svg/*.svg` and `src/icons/sprite.svg`.
- `workshop/src/icon-gallery.ts` imports it to render the gallery inline.

`build:icons` runs as the first step of `npm run build`, so the committed `svg/` and `sprite.svg` outputs regenerate from the source and can't silently drift. To add or edit an icon, change `icon-data.js` alone — the standalone SVGs, the sprite, and the workshop gallery all follow from that one edit.

## Workshop

`workshop/index.html` boots `src/main.ts`, which imports the kit CSS and every theme stylesheet through Vite (not `<link>` tags — cross-root `<link>` CSS parsed to zero rules in dev) and renders three tabs from separate modules: `token-viewer.ts`, `component-matrix.ts`, `icon-gallery.ts`. Each component section is its own module under `workshop/src/sections/` exporting a `Section` (`id`, `title`, `html`, optional `wire`) with its own snippets and demo wiring — `sections/index.ts` lists them in display order, `sections/shared.ts` holds the helpers more than one uses, and `component-matrix.ts` composes them: it concatenates every `html`, attaches the copy buttons and the shared press-button pass, then runs each `wire`. Theme switching sets `data-theme` on `<html>` and re-renders the token view.

## Consuming projects

Installed via Git reference (`"design-kit": "github:Bodegi/design-kit#main"`). Consumers `@import "design-kit/dist/index.css"` plus one `dist/themes/*.css`, then optionally override tokens in a later `:root` block. Public API is the token names and `.ui-*` class/anatomy contract — keep both stable across changes.

## Conventions

- **Open UI owns naming and anatomy.** Class names (`.ui-*`), `data-*` variants, and element structure follow the Open UI component-anatomy model (open-ui.org) — it is the sole authority for *how components are named and structured*. No individual app dictates names; apps contribute visuals (color, spacing, states, feel) only. Open UI publishes living explainers, not numbered releases, so we track its anatomy conventions rather than pinning a version. For components Open UI does not cover (app shell, sidebar nav, logo/watermark slots), extend the same conventions rather than inventing a new naming style.
- **WCAG AA is a hard gate.** No theme ships if any pairing fails the contrast check — body text 4.5:1, large text and UI parts 3.0:1.
  - *Where it runs.* `workshop/src/contrast.ts` holds the pairing list and the color math. The workshop's Token panel measures the active theme from computed styles and shows threshold, ratio and PASS/FAIL per row with a fail count at the top. `npm run check:contrast` runs the same pairings over every `src/themes/*.css` from the command line, prints a table per theme, and exits 1 on any failure; `npm run build` runs it after `typecheck` and before the icon, CSS and workshop steps, so a failing pairing fails the build and the CI deploy with it.
  - *What is measured.* The three text levels (`main`, `muted`, `dim`) on canvas and on surface, each intent's `-contrast` label on its fill, each intent as badge text on its own `-subtle` tint, `--color-border-focus` on canvas, and `--color-primary` on surface. `--color-border-strong` is measured on both surface and canvas at 3.0, because it draws the visual boundary of every field and a field sits on either ground — `--color-border-subtle` is not gated, since it draws decorative dividers rather than the edge of a control. Translucent tokens are composited first — an alpha foreground over its resolved background, an alpha background over the ground beneath it (a `-subtle` tint over surface over canvas) — so a ratio reflects what the eye sees rather than the raw literal.
  - *What that forces on a theme.* Derive `-contrast` and accent shades to pass rather than lifting an app color verbatim when it fails. Text on a tinted intent surface is `--color-text-main`, with the intent carried by the border (a 3.0:1 UI part); the intent color as its own badge text has little headroom on a dark surface, so the `-subtle` tints are tuned to hold 4.5:1 while staying at least 1.15:1 against surface. `.ui-tag` is the model here; `.ui-badge` still colors its label with the intent.
  - *Text over a picture is measured against a scrim, not the picture.* `--color-scrim` is an opaque near-black band and `--color-text-on-scrim` its ink (both baseline-only, since a scrim is dark in every theme), and `.ui-image[data-caption="overlay"]` keeps that band solid where the words sit, fading only above them, so the pairing the gate measures is the one the eye gets whatever the photograph is doing.
- Components reference semantic tokens only; add a new token to Tier 2 before using it in a component. A glyph a component cannot draw from borders (WebKit's `::-webkit-calendar-picker-indicator`) is a `mask-image` data URI carrying shape and no color at all, with `background-color` supplying the ink — so the mark recolors with the theme and no hex is baked into a component.
- **The focus ring stays whole and reachable.** A component shapes its content instead of clipping its box, and where it cannot, it makes room for the ring another way.
  - *Round the content, not the frame.* `.ui-avatar` and `.ui-image` round the `<img>` with `border-radius`, so an `<a>`/`<button>` frame keeps an unbroken ring and a status dot can sit proud of the edge.
  - *Clip only when the effect needs it.* An interactive `.ui-image` does clip — a hover zoom has to be contained — but the clip is its own `overflow: hidden`, which never applies to the element's own box-shadow, so the ring stays whole without an extra wrapper.
  - *Inset the ring where the component is the clipping container.* `details.ui-accordion` rounds its own corners, so its ring is drawn inset rather than outset.
  - *Lift a focused cell out of the paint order.* Where a component isolates its cells to stack a decoration behind them — `.ui-datepicker-grid td`, which paints the range band as a `z-index: -1` `::before` under the day pill — a `:has(:focus-visible)` rule raises the focused cell and its row, because a later sibling would otherwise cover the ring's overhang.
  - *Keep a hidden native control in the focus order.* `.ui-file` clips its input to a pixel rather than `display: none`, and draws the ring on the sibling affordance with `input:focus-visible + .part`.
- **No runtime — state keys off native/ARIA state.** The kit ships zero JS. Interactive components style their states from native or accessibility state (`aria-selected`, `aria-current`, `[open]`, `:indeterminate`, `[data-state]`) so the consuming app drives behavior by toggling that state — the visual and a11y state can never drift apart. Demos in the workshop supply their own wiring; the shipped CSS never does. Where an engine has a native trigger for a behavior the kit would otherwise leave to the app, the kit styles that path too: `.ui-tooltip[popover="hint"]` is the CSS tooltip's surface on a hint popover opened by an interest invoker (`interestfor` on the trigger), so Chromium gets the hover delay, the implicit anchor, the tooltip role and Escape-dismissal from the browser, and engines without it fall back to the hover/focus CSS tooltip.
- **A wrapper reads its state off the control it wraps.** Where a component puts a native input inside a shell (`.ui-number`, `.ui-combobox`, `.ui-richtext`, `.ui-file`), the shell's states come from `:has()` on that input — `:focus-visible`, `:user-invalid` / `[aria-invalid="true"]` / `[data-state="error"]`, `:read-only`, `:disabled` — so the app has one place to set state and it cannot drift. A shell that owns the border also clears the input's own ring, leaving exactly one. Both halves of that pairing sit behind `@supports selector(:has(*))`: putting the ring on the shell needs `:has()`, so clearing the control's ring is guarded by the same query and an engine without `:has()` keeps the control's own ring rather than none. `.ui-file` guards its whole state block the same way, so there the label still renders and the input's own disabled state still blocks the picker.
- **A flex row is not a list item.** A component that lays its rows out with `display: flex` stops generating the native `::marker`, so an ordered variant (`ol.ui-list`) numbers its rows from a CSS counter drawn in a `::before` inside the row.
- **A component that sets `display` has to restore `[hidden]`.** Any part an app shows and hides with the `hidden` attribute needs its own `[hidden] { display: none }` rule, because the component's own `display` declaration outranks the UA stylesheet's. That covers whole components (`.ui-btn`, `.ui-badge`, `.ui-alert`, `.ui-image`, `.ui-richtext`, `.ui-datepicker`, `.ui-skeleton`, `.ui-tag`, `.ui-file`) as well as rows and optional parts (`.ui-nav-item`, `.ui-list-item`, `.ui-breadcrumb-item`, `.ui-combobox-clear`, `.ui-combobox-empty`, `.ui-carousel-markers`, `.ui-image-badge`, `.ui-datepicker-footer`) — grep `[hidden]` across `src/components/` for the current set. A `[popover]` is the exception that still needs the rule: `.ui-tooltip[popover="hint"]` restates `display: none` for `:not(:popover-open)`, since the wrapper class's `display` outranks the UA's popover rule too.
- **A text range is marked one of two ways, and the kit styles both.** A range the app wraps is a real `<mark class="ui-richtext-highlight" data-intent>` — it stays in the accessibility tree and survives a copy, and takes `--color-text-main` over the intent's `-subtle` tint. A range nothing wraps is registered through the Custom Highlight API (`CSS.highlights.set(name, new Highlight(...ranges))`) and painted by `::highlight(name)`, which adds nothing to the DOM; `richtext.css` names `ui-spelling` and `ui-grammar` and styles them inside `@supports selector(::highlight(x))`, using only decoration and color, since those are all a highlight pseudo honors. A field that grows with its content opts in with `data-autoresize`, which sets `field-sizing: content` — on `.ui-richtext` and on a bare `textarea.ui-textarea` alike; engines without it keep the fixed box.
- **Motion respects `prefers-reduced-motion`.** Any component with an entrance/loop/transition (toast, tooltip, progress, meter, …) neutralizes or stills it under `@media (prefers-reduced-motion: reduce)`.
- **Shape (corner radius) is a system constant, not a theme knob.** It lives in the Tier-1 `--radius-*` scale and the Tier-2 roles `--radius-inline` (2px, marks at text scale) / `--radius-nav` (6px) / `--radius-control` (10px, buttons & inputs) / `--radius-base` (12px, panels & cards). Themes set **color tokens only** and must not override radius, so every app shares one shape and differs by color alone. A component rounds to a role — `--radius-nav` for rows, option cells and the small buttons inside a field, `--radius-control` for fields, `--radius-base` for panels, popovers and listboxes — alongside `--radius-full` for pills and dots and `--radius-inline` for `<code>`, `<mark>` and the checkbox tick box. The intermediate Tier-1 steps are the roles' raw material rather than a component's vocabulary.
- **A treatment repeated across components is shared once, by whichever of three mechanisms the repetition allows.** In every case the markup gains no extra class — components agree on a definition, never on a wrapper.
  - *A repeated color or shadow becomes a Tier-2 token.* `--color-bg-current` + `--shadow-current-bar` carry the current/selected row for `.ui-nav`, `.ui-list` and `.ui-accordion-group`. `.ui-table` takes the bar and not the ground: a selected row is tinted `--color-primary-subtle` so it still reads as selected inside a striped body.
  - *Repeated declarations two selectors can both carry become one rule with a selector list.* `.ui-tooltip-content` and `.ui-tooltip[popover="hint"]` are two renderings of one tooltip, so its surface and all four arrow placements are written once across both.
  - *Repeated geometry that no selector list can join is shared as private properties with the same values at each site.* `--_chevron-size`/`--_chevron-weight`/`--_chevron-rotate` at md 8px/2px and sm 6px/1.5px, and `--_x-size`/`--_x-weight` at md 9px and sm 7px — a square showing its right and bottom borders for the chevron, two crossed bars for the ×. `.ui-carousel` does the same for its dot (`--_marker-size`, `--_marker-ring`, `--_marker-current-width`) and arrow inset, because its second control path is a `::scroll-marker` that only parses inside `@supports` and would invalidate a shared rule everywhere else.
  - *Where none of the three fits, name the canonical definition in a comment.* `.ui-image`'s loading shimmer repeats `.ui-skeleton`'s, because a `@keyframes` name is global and reusing it would couple the two files; both say so, and both have to change together.
- New theme: scope to both `[data-theme="x"]` and `:root[data-theme="x"]`, and define the full intent set (`success`/`warning`/`danger`/`info` and their `-subtle`/`-contrast`) so it reads correctly against its own surfaces rather than falling back to the dark baseline.
